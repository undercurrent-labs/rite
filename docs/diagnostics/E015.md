# E015 — a pipeline's result cannot be an operand

`→` is looser than every binary operator, so the value on its left is finished
before it is piped. That is what makes the input side read as it is written:

```rite exec
a ← 2
b ← 3
! @console.println(a + b → str)   // (a + b) → str
```

The cost lands on the other side. Nothing below `→` in the precedence chain can
consume an operator that follows a pipeline, so this is rejected rather than
regrouped:

```rite compile_fail
xs ← [1, 2, 3]
xs → count > 2
```

Parenthesise the pipeline to use its result:

```rite exec
xs ← [1, 2, 3]
! @console.println(str((xs → count) > 2))
```

## Why it is not simply allowed

An infix operator cannot be looser than `+` on its left and tighter than `+` on
its right — those are contradictory positions in one precedence chain. `→` has to
pick a side, and every arrangement has been tried:

| Arrangement | `a + b → str` | `xs → count > 2` |
|---|---|---|
| Loose, stages as full expressions | `(a + b) → str` | `xs → (count > 2)` — died at runtime |
| Tight, stages at postfix | `a + (b → str)` — silently | `(xs → count) > 2` |
| **Loose, stages at postfix** (current) | `(a + b) → str` | **E015** |

The first two each answer one case by quietly getting the other wrong. This one
gets the input side right and makes the other case say so.

`|>` in F#, Elixir and Elm makes the same trade — there `xs |> length + 1` is a
type error rather than a parse error, but the parentheses are equally required.

## Stages are not operator expressions

A stage is a name, a call, or a trailing-block call. `xs → count + 1` could only
mean `xs → (count + 1)`, and `count + 1` cannot be applied to a list. The operator
is therefore reported at the pipeline rather than absorbed into the stage.
